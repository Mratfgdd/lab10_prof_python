Settings (pydantic-settings) читає змінні середовища, а для локальної розробки – файл .env; змінна середовища має пріоритет над .env. Значення перевіряються під час старту: недопустимий APP_ENV чи від'ємний CONFLICT_RETRIES зупиняють сервіс з помилкою, а не приводять до некоректної роботи.

class Settings(BaseSettings):
    model_config = SettingsConfigDict(env_file=".env", env_file_encoding="utf-8", extra="ignore")

    app_name: str = "Bank Account Service"
    app_env: Literal["development", "test", "production"] = "development"
    database_url: str = "sqlite:///bank.db"
    log_level: Literal["DEBUG", "INFO", "WARNING", "ERROR"] = "INFO"
    conflict_retries: int = Field(default=3, ge=0, le=10)
    # Якщо задано - зміни даних (POST/PATCH/DELETE) вимагають заголовок X-API-Key.
    api_token: SecretStr | None = None

    @field_validator("log_level", mode="before")
    @classmethod
    def upper_level(cls, value: object) -> object:
        return value.upper() if isinstance(value, str) else value

    @field_validator("api_token", mode="before")
    @classmethod
    def empty_token_is_unset(cls, value: object) -> object:
        # «API_TOKEN=» з .env.example означає «не задано», а не порожній пароль.
        return None if isinstance(value, str) and not value.strip() else value

    @property
    def safe_database_url(self) -> str:
        """URL БД для логів: пароль замінено на ***."""
        return make_url(self.database_url).render_as_string(hide_password=True)

Secrets. У коді, README, Dockerfile і Git немає жодного справжнього пароля чи токена. Секрет API_TOKEN надходить лише із середовища: з файлу .env, з docker run --env-file або з GitHub Actions secrets. .env внесено в .gitignore і .dockerignore, тож він не потрапляє ні в репозиторій, ні в образ. Тип SecretStr не показує значення в repr і логах, пароль у DATABASE_URL маскується в лозі запуску, а команда config показує конфігурацію з прихованими секретами. 4. Docker: Dockerfile, .dockerignore, запуск контейнера

# syntax=docker/dockerfile:1

# ---------- Етап 1: збірка wheel (інструменти збірки не потрапляють у фінальний образ)
FROM python:3.12-slim AS builder
WORKDIR /build
RUN python -m pip install --no-cache-dir "build>=1.2"
COPY pyproject.toml README.md LICENSE ./
COPY src ./src
RUN python -m build --wheel --outdir /dist

# ---------- Етап 2: runtime - лише Python, встановлений wheel і його залежності
FROM python:3.12-slim
ENV PYTHONDONTWRITEBYTECODE=1 \
    PYTHONUNBUFFERED=1 \
    PIP_NO_CACHE_DIR=1 \
    PIP_DISABLE_PIP_VERSION_CHECK=1 \
    APP_ENV=production \
    LOG_LEVEL=INFO \
    DATABASE_URL=sqlite:////app/data/bank.db
WORKDIR /app
COPY --from=builder /dist/*.whl /tmp/
RUN python -m pip install /tmp/*.whl \
    && rm /tmp/*.whl \
    && useradd --create-home --uid 1000 appuser \
    && mkdir -p /app/data \
    && chown appuser:appuser /app/data
# Не root: процес у контейнері не має прав адміністратора.
USER appuser
# SQLite-файл - у volume, щоб дані переживали перезапуск і оновлення контейнера.
VOLUME ["/app/data"]
EXPOSE 8000
HEALTHCHECK --interval=30s --timeout=3s --start-period=15s --start-interval=2s --retries=3 \
    CMD python -c "import sys, urllib.request; sys.exit(urllib.request.urlopen('http://127.0.0.1:8000/health', timeout=2).status != 200)"
# serve застосовує міграції (alembic upgrade head) і запускає uvicorn.
CMD ["bank-account-service", "serve", "--host", "0.0.0.0", "--port", "8000"]

Образ двоетапний (multi-stage). Етап builder збирає wheel, і інструменти збірки до фінального образу не потрапляють. Runtime-етап на базі python:3.12-slim встановлює лише wheel і його залежності. Процес працює від користувача appuser, не від root. SQLite-файл лежить у volume /app/data і переживає перезапуск та оновлення контейнера. HEALTHCHECK кожні 30 с перевіряє /health. Команда serve спершу застосовує міграції (автоматичні міграції при deployment), а потім запускає uvicorn у production-режимі, без --reload. .dockerignore залишає в build context лише pyproject.toml, README, LICENSE і src/, тобто без .env, тестів, кешів і .git; секретів в образі немає, вони передаються під час запуску.

5. CI/CD: GitHub Actions

Workflow .github/workflows/ci.yml запускається на кожен push у main, на pull request і вручну. Права обмежено: contents: read. Він має два jobs:

  • quality – матриця Python 3.11 і 3.12;
  • docker – запускається лише після успішного quality (needs); збирає образ із тегами ci і коротким SHA commit, запускає контейнер і чекає відповіді /health (smoke test).

Секрет береться з налаштувань репозиторію (${{ secrets.API_TOKEN }}) і передається в контейнер як -e API_TOKEN без значення в команді.

# ci.yml (фрагмент, без коментарів)
name: CI

on:
  push:
    branches: [main]
  pull_request:
  workflow_dispatch:

  contents: read

jobs:
  quality:
    name: Lint, types, tests, build (Python ${{ matrix.python-version }})
    runs-on: ubuntu-latest
    strategy:
      fail-fast: false
      matrix:
        python-version: ["3.11", "3.12"]
    steps:
      ...            # кроки job quality - у таблиці 2 і на рисунку 6

  docker:
    name: Docker build and smoke test
    needs: quality
    runs-on: ubuntu-latest
    env:
      API_TOKEN: ${{ secrets.API_TOKEN }}
    steps:
      - name: Checkout
        uses: actions/checkout@v4

      - name: Build image
        run: docker build -t bank-account-service:ci -t "bank-account-service:${GITHUB_SHA::7}" .

      - name: Run container and check /health
        run: |
          docker run -d --name api -e APP_ENV=production -e API_TOKEN bank-account-service:ci
          for attempt in $(seq 1 30); do
            if docker exec api python -c "import urllib.request; print(urllib.request.urlopen('http://127.0.0.1:8000/health').read().decode())"; then
              docker logs api
              exit 0
            fi
            sleep 1
          done
          docker logs api
          exit 1

Локальний прогін виявив реальну помилку, якої не було видно на Windows: на Python 3.13 приблизно кожен четвертий запуск тестів падав з ResourceWarning: unclosed database. Причина була в клієнті з ЛР8: asyncio.gather після відповіді 404 на один запит рахунку лишав другий запит працювати після повернення результату. Його обробку на сервері скасовували вже після закриття пулу з'єднань, а синхронна yield-залежність FastAPI при скасуванні не закриває сесію. Виправлення: у клієнті asyncio.TaskGroup, який скасовує сусідній запит і чекає його завершення; на сервері асинхронна залежність, що закриває сесію в finally; try/finally у lifespan. Після виправлення 25 повторних прогонів пройшли без помилок.
